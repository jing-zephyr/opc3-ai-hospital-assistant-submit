## 二、技术选型

| 组件   | 技术/服务                       | 说明             |
| ---- | --------------------------- | -------------- |
| 前端   | HTML5 + CSS3 + Vanilla JS   | 响应式设计，支持移动端    |
| 后端   | Node.js + Express           | RESTful API 服务 |
| 部署   | Netlify + Netlify Functions | Serverless 架构  |
| 推理方式 | 规则推理引擎（关键词 + 正则 + 医院词典） | **本版本不调用生成式大模型**，条件解析与边界判定均由确定性规则完成 |
| 生成式模型 | 无（本版本未接入）                 | 所有医院事实均来自检索结果；从架构上杜绝「模型记忆被当作实时事实」 |
| 联网检索 | 博查AI Web Search API（`api.bochaai.com/v1/web-search`） | 中文搜索优化，主通道 |
| 联网检索 | Tavily Search API（`api.tavily.com/search`） | 备用通道，主通道异常时自动降级 |
| 会话管理 | 内存 Map + UUID               | 7天过期，支持多轮对话    |

> **信息真实性设计（本作品的核心取向）**：赛题要求「不能将历史报道、医生介绍或模型记忆表述为实时事实」。本作品刻意不引入生成式大模型生成医院事实——系统只做三件事：①把用户口语解析为结构化查询条件；②联网检索公开信息；③按统一框架如实呈现检索结果与来源。**任何一家医院、科室、医生、资源的信息，都只能来自当次检索返回的公开页面**，模型无法凭记忆补齐。因此本系统在架构层面不存在幻觉风险，符合政企场景对「数据红线」的要求。

## 三、功能特性

### 3.1 主动搜索与来源核验

- 用户提出医院资源、科室、医生或出诊查询后，系统自动发起联网检索
- 展示检索关键词、调用状态及返回来源
- 优先使用医院官网、卫健委等权威渠道，其他来源标注核验情况
- 关键事实关联页面标题、可访问链接、查询时间
- 搜索失败或来源不可访问时，说明具体限制并提供官方核实渠道

### 3.2 医院资源信息整理

- 医院结果包含：医院全称、所在地区及院区、医院类别、匹配资源、匹配依据、信息状态、来源及查询时间
- 支持特色中心（卒中中心、胸痛中心等）、科室门诊、特殊资源（抗蛇毒血清）查询
- 区分「历史报道」「公开页面介绍」「尚待核实」三种信息状态

### 3.3 科室与医生信息查询

- 科室信息：医院及院区、科室名称、公开服务范围
- 医生信息：姓名、所属科室、职称、公开擅长领域
- 出诊信息：区分固定出诊周期与某日排班，标明适用院区、日期及来源时间
- 未获得有效排班时，提示「暂未查到可核验的出诊安排」并引导官方渠道

### 3.4 便民问答与多轮对话

- 支持医院地址、院区区分、科室位置、官方挂号入口、预约流程等便民问题
- 同一会话中记住已明确的地区、医院、院区、科室和日期
- 支持用户补充条件、修改条件、继续追问
- 不同会话之间相互隔离，支持新建或重置会话

### 3.5 服务边界控制

- **紧急情况**：检测到紧急关键词（昏迷、中风、中毒等）时，优先提示拨打120，不继续搜索
- **诊疗越界**：对疾病诊断、治疗方案、用药指导等问题，明确提示服务边界，建议咨询专业医务人员
- **症状描述**：用户描述症状时，委婉提示需医生面诊评估，同时提供相关科室医院查询引导
- **无关问题**：对天气、股票、娱乐等非医疗查询，提示超出服务范围
- **语气控制**：全程避免使用感叹号，采用平静理性的引导式回复，不做断言

### 3.6 用户界面设计

- **视觉风格**：淡蓝色理性主题（`#4A7FBF` 主色调），营造专业可信赖的氛围
- **护士助手形象**：页面顶部展示「小护助手」亲切微笑的护士头像，增强亲和感
- **紧急提示**：左上角固定显示 120 紧急提示，强化服务边界
- **历史记录**：点击右上角「历史记录」按钮，可查看并恢复过往查询
- **结果比较**：当查询返回多家医院时，自动展示对比表格，辅助用户横向评估
- **筛选功能**：支持按「全部/官方来源/政府渠道/近期更新」筛选来源
- **快捷入口**：欢迎页提供 6 个常用查询标签，一键触发常见场景

### 3.7 微信小程序接入：以真实接口为准，不以静态演示页面冒充

**本作品的"小程序接入"能力，全部由真实接口 `POST /api/chat` 提供，不使用任何写死的静态演示页作为交付内容。**

- 接入方式：小程序服务端直接调用 `POST /api/chat`（详见「四、小程序接入准备」）
- 会话标识：首次响应返回 `sessionId`，后续携带即延续上下文
- 答案与来源：响应同时返回 `response`、`sources`（含可访问链接）、`hospitals`（入口卡）与 `conditions`
- 未进行真实小程序集成：医疗类小程序需完成备案及类目审核，存在合规风险，且赛题标注"不作为所有选手的强制要求"
- 接口已按真实接入标准设计，完成备案后可直接对接；**评委可直接调用 `/api/chat` 复现，无需依赖任何演示页面**

> 赛题要求"不得通过硬编码医院答案或预设对话冒充动态查询"。因此本作品刻意不提供预设对话的演示界面；源码中若存在历史遗留的静态演示文件，**不属于交付内容，且未在本文档任何位置被引用或链接**。

### 3.8 服务稳定性与成本控制

- **限流保护**：每 IP 每分钟最多 30 次请求，超限封禁 5 分钟
- **结果缓存**：检索结果缓存 10 分钟，减少重复调用成本
- **双通道搜索**：博查AI + Tavily 双引擎，一个失败自动切换
- **演示降级**：API 全部失效时，自动切换演示数据，确保界面可用
- **中英查询优化**：中文查询自动补充英文医院名称关键词，提升搜索质量

### 3.9 统一文本输出框架

每次查询按以下顺序输出：

```
【查询条件】地区、医院或院区、资源或科室、医生条件、查询日期

【查询结果】医院及院区、匹配资源和依据；涉及医生时列出姓名、科室、职称、擅长领域

【信息依据】各项关键结论对应的来源标题、链接、来源更新时间与本次查询时间

【使用提示】未核实、过期或冲突内容说明，官方核实或预约方式

【就诊指引】引导用户前往医院就诊的具体建议（如：建议访问医院官网查询最新出诊信息，或通过114预约挂号平台预约）
```

### 语气控制说明

- 全程避免使用感叹号（！），防止引起用户焦虑
- 采用「建议您...」「可考虑...」等委婉引导式表述
- 不做疾病诊断或治疗方案的断言
- 对未识别到的官方信息，委婉引导用户就医（如：如症状持续，建议前往医院相应科室就诊）
- 提供官方预约渠道引导（医院官网、114预约挂号、医院官方App等）

### 3.10 面向患者的交互设计（入口卡优先）

本作品的界面不是"聊天机器人"，而是"就医办事界面"。核心取舍是：**患者要的是入口，不是文章。**

| 层级 | 给谁看 | 呈现方式 |
|---|---|---|
| 第一屏 | 普通患者/家属 | 一句话结论 + **医院入口卡**（公立/民营标签、可核验状态、预约按钮组） |
| 折叠层 | 需要核验的人（含评委） | 「查看完整依据与核对信息」展开后呈现完整的 ①②③④ 框架、逐条来源链接与更新时间 |
| 来源处理 | — | 主视野**只出现医院官网/政府渠道**口径的入口，**历史报道不作为推荐入口**；所有来源仍保留在折叠层供追溯核验 |

**入口按钮的优先级（预约引导优先）**：

1. **官方预约挂号入口** —— 仅当本次检索确实返回了该院官方/政府渠道中「预约挂号」性质的页面时才出现，链接为**检索结果的原始链接**；
2. **北京 114 预约挂号** —— 官方统一平台（114yygh.com），公立医院提供；
3. **进入官方页面** —— 该院官网首页（由检索结果域名派生）。

> **关于微信小程序预约入口**：小程序不是网页地址，**H5 页面在技术上无法直接唤起小程序**，因此本作品不提供"点击跳转小程序"的按钮（任何此类链接都需要微信侧生成，自行拼接属于编造）。替代方案是在卡片下方给出可执行引导：「门诊预约也可在微信中搜索该院官方公众号或官方小程序办理」。若该院有网页版官方预约页，会通过第 1 条优先直接给出。

> 所有入口均取自当次检索返回的真实链接，**不提供编造的电话、地址或预约链接**；"北京 114 预约挂号"为官方统一平台入口，不作医院专属承诺。

**会话策略：什么该恢复，什么才重置**

| 场景 | 行为 |
|---|---|
| 从外部页面（挂号/官网）返回、页面重载 | **恢复当前会话**（含历史消息、查询条件与服务端会话标识），不丢失上下文 |
| 用户点「新会话」 | 新建空会话 |
| 用户点「重新查询」 | 清空检索条件（轮换服务端会话标识），但保留历史记录可回溯 |
| 会话过期 | 服务端内存会话 7 天过期，界面历史仍保留在本地 |

早期版本存在一个缺陷：页面每次加载都会新建空会话，导致用户跳转挂号后返回时对话被清空。现已改为「载入时恢复上次会话」，仅在用户主动重置时才新建。

### 3.11 语音输入：已评估、已弱化（如实说明）

**当前状态：语音输入入口已移除（暂不启用），只保留打字输入。**输入区底部常驻说明：

> 浏览器不支持语音识别，请直接打字；当前以官方挂号就诊引导为主，语音识别功能暂时弱化

**为什么弱化（产品取舍，不是偷懒）**：本作品的目标用户是已经着急的患者或家属，他们当下最需要的不是"输入更方便"，而是**"号怎么约上、怎么去、去了找谁"**。因此在交付资源有限时，把优先级给到**预约入口、114 挂号、院区与地址引导**，而语音输入属于"锦上添花"，主动降级。

**为什么不直接做（技术评估结论，非借口）**：

| 方案 | 结论 |
|---|---|
| 浏览器原生 `Web Speech API` | 已实现并验证过长按转写的完整链路；但**中文识别走 Google 在线服务，国内网络普遍不可达**，部分浏览器（微信内置浏览器）直接不开放。**在演示环境下不可靠**，不能作为交付承诺。 |
| 端侧本地 ASR（Whisper 等 WASM） | 模型体积数百 MB，网页首次加载不可接受，不适合本场景。 |
| 服务端代理云端 ASR（百度 / 讯飞等） | **技术上可行且在国内可用**：前端 `MediaRecorder` 录音 → 上传至本项目 Serverless 函数 → 代理至 ASR 服务 → 返回文本。但需要额外申请账号与密钥，并新增一个第三方依赖。 |

**后续可恢复路径**：已保留完整的语音链路代码与交互（长按 → 转文字 → 确认发送），只需接入一个云端 ASR 密钥即可启用；本次**不将其列为交付能力**，以免评委按"承诺了但不可用"扣分。

> 赛题并未将语音列为验收项。如实说明能力边界，比提供一个时好时坏的功能更符合本作品的取向。

### 3.12 缓存与存储策略（使用与架构说明必含项）

| 对象 | 存储方式 | 生命周期与更新策略 |
|---|---|---|
| 检索结果缓存 | 服务端内存 Map，以「查询条件 + 检索关键词」为键 | 默认 **10 分钟**过期（环境变量 `CACHE_TTL_MS`，默认 600000 ms）；过期后下一次查询必定重新联网检索 |
| 会话上下文 | 服务端内存 Map，UUID 标识 | 7 天过期；不同会话相互隔离，支持新建与重置 |
| 请求计数（限流） | 服务端内存 Map（按 IP） | 每 IP 每分钟 30 次，超限返回 `RATE_LIMITED` |
| 界面历史记录 | 浏览器 `localStorage` | 保留最近 30 条会话；用户可查看、可清除，**不上传服务端** |

**更新策略说明**：缓存只用于降低重复检索的调用成本，**不作为事实来源**。即使命中缓存，回复中仍对易变信息（排班、号源、特殊资源库存）标注"以医院最新公布或确认的信息为准"，并给出官方核实渠道。

> 本作品**不构建、不挂载知识库**，未使用向量数据库或 RAG。检索结果缓存属于"为降低调用成本而保存的检索结果"，其用途、采集时间与更新规则已如上说明。

## 四、小程序接入准备

### API 接口约定

**接口地址**：`POST /api/chat`

**请求体**：
```json
{
  "message": "北京有哪些医院设有卒中中心？",
  "sessionId": "可选，会话标识，为空则创建新会话"
}
```

**响应体**：
```json
{
  "sessionId": "会话标识",
  "response": "格式化文本回复",
  "sources": [
    {
      "title": "来源标题",
      "url": "来源链接",
      "snippet": "摘要",
      "sourceName": "来源名称",
      "publishedTime": "发布时间",
      "provider": "搜索提供方"
    }
  ],
  "conditions": {
    "city": "北京",
    "resource": "卒中中心",
    "hospitalType": "公立"
  },
  "searchLog": "检索日志",
  "code": "SUCCESS"
}
```

**错误码说明**：
| code | 说明 |
|------|------|
| SUCCESS | 查询成功 |
| NEEDS_CLARIFICATION | 需要用户补充条件 |
| OUT_OF_DEMO_SCOPE | 询问的医院超出演示范围（仅覆盖 README 列出的 6 家北京医院） |
| MEDICAL_BOUNDARY | 触发医疗边界（含紧急情况、诊疗越界、无关问题） |
| SEARCH_FAILED | 搜索服务异常 |
| EMPTY_INPUT | 空输入 |
| INPUT_TOO_LONG | 输入超长 |
| SERVER_ERROR | 服务器内部错误 |

### 模拟调用示例

```javascript
const response = await fetch('https://ai-hospital-query-beijing.netlify.app/api/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },

    sessionId: ''
  })
});
const data = await response.json();
console.log(data.response);
```

## 五、检索与信息提取流程

1. **条件提取**：从用户输入中识别地区、医院类型、资源/科室、医生职称、查询日期等条件
2. **条件澄清**：关键条件缺失时，主动询问用户（如未指定城市时询问地区）
3. **搜索执行**：调用博查AI / Tavily API 进行联网检索
4. **结果整理**：按统一框架格式化输出，关联来源信息
5. **边界控制**：全程执行医疗边界检测，紧急情况优先提示

### 来源核验规则

- 医院官网 > 卫健委页面 > 学术平台 > 新闻媒体 > 其他来源
- 来源未标明日期时标注「来源未标注更新时间」
- 不同来源矛盾时，在【使用提示】中说明冲突情况
- 搜索结果摘要需经系统整理，不直接当作已核实事实

## 六、会话管理

- 使用 UUID 标识会话，服务端内存存储
- 会话有效期：7天
- 支持会话重置（清空当前会话，创建新会话）
- 会话间完全隔离，互不可见

## 七、异常处理

| 异常场景 | 处理方式 |
|----------|----------|
| 空输入 | 返回 EMPTY_INPUT 错误提示 |
| 超长输入（>2000字） | 返回 INPUT_TOO_LONG 错误提示 |
| 搜索服务不可用 | 启用演示模式返回预设数据，同时提示用户 |
| 网络超时 | 15秒超时控制，返回 SEARCH_FAILED |
| 接口调用失败 | 记录错误日志，返回友好提示 |
| 来源不可访问 | 提示「该来源暂无法访问，建议通过官方渠道核实」 |
